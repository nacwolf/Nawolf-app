Redesign how overhead and labor costs are calculated per SKU.
Both use per-SKU production details entered on the SKU page.
No global monthly units figure anywhere.

DATABASE CHANGES
────────────────────────────────────────────

Add these columns to production_config_history
(and sku_production_config if it exists):

  production_days_per_month INTEGER NOT NULL DEFAULT 20
  -- How many days per month this SKU is produced.

Remove the column monthly_units from overhead_configs.

Add one column to overhead_configs (organisation-level):

  operating_days_per_year INTEGER NOT NULL DEFAULT 250
  -- How many days per year the factory actually runs.
  -- Typically 250 (5 days/week, 50 weeks).
  -- Used to convert annual fixed costs to a daily/monthly rate
  -- and to sense-check per-SKU production days.

New table if not exists:
  production_config_history columns needed:
    id, org_id, sku_id, effective_date,
    units_per_day, carton_size, shift_hours,
    production_days_per_month,
    team_member_ids,
    labor_per_unit,       -- calculated, stored

    total_day_cost,
    change_reason, change_note,
    created_by, created_at

  Input: number, default 250, range 1–365
  Hint: "Count only actual production days — exclude
         weekends, public holidays, and planned shutdowns.
         Most food factories run 220–260 days per year.
         e.g. 250 = 5 days/week, 50 working weeks
              220 = 5 days/week with longer holidays
              300 = includes some Saturdays"

Show a read-only confirmation below:
  "That is ~X days per month on average
   (X days/year ÷ 12 months)"
  Calculated as: operating_days_per_year / 12, rounded to 1dp.

This single number is used in two ways:
  1. To convert annual fixed costs (like annual
     certification fees) to a monthly equivalent
  2. To validate per-SKU production days —
     a SKU cannot be produced more days per month
     than the factory operates

────────────────────────────────────────────
CALCULATION LOGIC — server side
────────────────────────────────────────────

Run this every time production setup is saved for a SKU:

  -- Step 1: Labor per unit (unchanged)
  total_loaded_rate = SUM(
    member.hourly_wage * (1 + member.oncost_percent / 100)
    FOR EACH member_id IN team_member_ids
  )
  total_day_units   = units_per_day * carton_size
  labor_per_unit    = (total_loaded_rate * shift_hours)
                      / total_day_units
  total_day_cost    = total_loaded_rate * shift_hours

  -- Step 2: Overhead per unit
  -- Uses per-SKU monthly volume, not a global figure
  total_monthly_fixed   = SUM(all overhead cost items)
  sku_monthly_units     = units_per_day
                          * carton_size
                          * production_days_per_month
  overhead_per_unit     = total_monthly_fixed
                          / sku_monthly_units

  NOTE: total_monthly_fixed is already stored as monthly
  amounts in overhead cost items. If any cost item was
  entered as an annual amount (e.g. annual certification
  fee), convert it:
    monthly_amount = annual_amount / (operating_days_per_year / 12 / (operating_days_per_year / 12))
  Simplest approach: store all overhead items as monthly.
  Add a field on each overhead cost item:
    frequency: 'monthly' | 'annual'
  If annual: monthly_equivalent = amount / 12
  Always use monthly_equivalent in the overhead pool total.

  -- Step 3: Store everything
  INSERT into production_config_history:
    all input fields + labor_per_unit + overhead_per_unit
    + change_reason + change_note

  -- Step 4: Update ingredient prices
  INSERT new ingredient_prices row for "Production Labor"
    for this SKU: price = labor_per_unit,
    effective_date = today,
    reason = built from change_reason + change_note

  INSERT new ingredient_prices row for "Overhead Allocation"
    for this SKU: price = overhead_per_unit,
    effective_date = today,
    reason = "Overhead: €X,XXX/mo ÷ X,XXX units/mo
              (X days/mo × X units/day)"

  -- Step 5: Trigger snapshot cascade
  Recalculate COGS for this SKU and write a new
  sku_snapshots row as normal.

────────────────────────────────────────────
WHEN TO RECALCULATE AUTOMATICALLY
────────────────────────────────────────────

Recalculate labor + overhead for a specific SKU when:
  - Any production setup field changes on that SKU
    (units_per_day, shift_hours, team_member_ids,
     carton_size, production_days_per_month)
  - A team_member wage or oncost changes in cost library
    → recalculate ALL SKUs that include that team member

Recalculate overhead only (not labor) for ALL SKUs when:
  - Any overhead cost item is added, updated, or removed
  - operating_days_per_year is changed in overhead settings
    (changing factory days changes monthly_equivalent of
     any annual cost items, which changes the overhead pool)
  → Loop through every SKU, recalculate overhead_per_unit,
    insert new ingredient_prices row, trigger snapshot cascade

Confirmations after bulk recalculation:
  Overhead change: "Overhead update affected 6 SKUs.
                   All margins recalculated."
  Wage change:     "Ana's wage update affected 4 SKUs:
                   Sourdough Loaf, Brioche Bun, Rye Crackers,
                   Seeded Flatbread. All costs recalculated."
  Factory days:    "Factory operating days updated to 240.
                   Overhead recalculated for 6 SKUs."
